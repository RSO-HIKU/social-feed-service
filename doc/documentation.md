# Social Feed Service - Technical Documentation

## Overview

The **Social Feed Service** is a microservice responsible for managing user posts and delivering personalized feeds based on social relationships within the HIKU hiking application. It consumes follow events from RabbitMQ, stores follow relationships, and provides endpoints to create and delete posts and view following users posts.

## Business Logic

### How It Works

The Social Feed Service provides social networking functionality for the HIKU hiking application by managing posts and delivering personalized feeds based on user relationships.

**Post Creation & Management**
- Users create posts containing hiking content (title, description, images)
- Each post includes user identification, timestamp, and content details
- Users can view posts from people they follow and delete their own posts

**Personalized Feed Delivery**
- When users request their feed, the service retrieves posts only from people they follow
- Posts are ordered chronologically (newest first) for easy browsing
- The feed is generated by querying a local copy of follow relationships

**Follow Relationship Synchronization**
- The service consumes follow/unfollow events from RabbitMQ published by the User Service
- When a follow event arrives, it adds the relationship to the local `follows` table
- When an unfollow event arrives, it removes the relationship from the local table
- This event-driven approach keeps the local copy synchronized with the User Service (source of truth)

**Key Design Decision**: The service maintains a **local replica** of follow relationships to optimize feed generation. By caching these relationships locally and synchronizing via events, the service can generate feeds quickly without cross-service API calls.

## Database Schema

### Schema: `social_feed_service`

#### Table: `posts`

Stores user-generated posts and automated content.

| Column | Type | Constraints | Description |
|--------|------|-------------|-------------|
| `id` | BIGSERIAL | PRIMARY KEY | Auto-increment post ID |
| `user_id` | VARCHAR(255) | NOT NULL | User ID from User Service (UUID) |
| `username` | VARCHAR(255) | - | Username for display purposes |
| `title` | VARCHAR(255) | - | Post title |
| `content` | VARCHAR(2000) | - | Post content/description |
| `post_image_url` | VARCHAR(500) | - | URL to post image |
| `created_at` | TIMESTAMP | NOT NULL | Post creation timestamp |
| `automated` | BOOLEAN | NOT NULL | True for system-generated posts |

**Indexes**:
- Primary key on `id`
- Consider adding index on `user_id` for user post queries
- Consider adding index on `created_at` for feed sorting

#### Table: `follows`

Local cache of follow relationships (synced via RabbitMQ).

| Column | Type | Constraints | Description |
|--------|------|-------------|-------------|
| `id` | BIGSERIAL | PRIMARY KEY | Auto-increment ID |
| `follower_id` | VARCHAR(255) | NOT NULL | User who follows (UUID) |
| `following_id` | VARCHAR(255) | NOT NULL | User being followed (UUID) |
| `created_at` | TIMESTAMP WITH TIME ZONE | NOT NULL | Relationship creation timestamp |

**Unique Constraint**: `(follower_id, following_id)` - prevents duplicate follows

**Note**: This table is a **read replica** of the User Service's follow relationships, synchronized via RabbitMQ events.

### Database Migration

Database schema is managed using **Flyway** migrations located in `src/main/resources/db/migration/`.

Rules when working with migrations:
- Each migration has to follow the naming convention: VX__\<short name\>, where X is the next number that hasn't been used yet.
- Database migrations must be idempotent. You must not delete already existing and applied migrations.

Migrations run automatically via Kubernetes Job (see `helm/templates/migrate-job.yaml`).

## Local Development

Building images and deployment for local development is handled by Skaffold. By running the command **skaffold dev** in the root folder of the repository in a terminal window will make Skaffold automatically build and deploy the service to your local Minikube cluster. Skaffold watches your local files and when you save a change, Skaffold automatically applies it.
